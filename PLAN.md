# veldb — план работ

In-memory колоночная СУБД под ARM (Apple silicon / Raspberry Pi) с векторным поиском.

## Ключевые решения (и почему)

| Решение | Почему |
|---|---|
| Rust | ARM NEON интринсики из `std::arch::aarch64`, нет GC-пауз, tonic/axum из коробки |
| Колоночное хранение | ClickBench — OLAP-бенчмарк. Строчный движок его не пройдёт. Векторы тоже колонка (плотный `f32`) |
| Один крейт, бинарники `veldb`/`veldbctl` | Меньше файлов — меньше сборки. Workspace добавим, когда реально разъедется |
| `sqlparser` вместо своего парсера | Свой SQL-парсер это 5k строк, которые ничего не доказывают |
| Свой бинарный формат снапшота | Колонки — это уже плотные массивы. `memcpy` вместо serde: быстрее и меньше кода |
| Строки-арена вместо словаря | Словарь выигрывает только на низкой кардинальности; на `URL` из ClickBench его хеш-таблица съедает больше, чем экономит. Словарное кодирование — пункт фазы тюнинга |
| Flat-индекс векторов до HNSW | На 1M×768 flat + NEON даёт ~50мс. HNSW добавляем, когда померяем, что мало |

## Честное ограничение по ClickBench

Полный ClickBench — 100M строк, ~70 ГБ в raw TSV. In-memory на 16 ГБ Mac и тем более
на Raspberry Pi это не влезет физически. План:

- основной прогон: **10M строк** (`hits` subset), 43 запроса, сравнение с ClickHouse на той же машине;
- на полных 100M — только с dictionary+RLE сжатием строк и замером, сколько реально влезает;
- в отчёте всегда указывается размер датасета. Сравнение «10M у нас vs 100M у ClickHouse» — это не бенчмарк.

## Фазы

Каждая фаза заканчивается зелёными тестами. Тесты пишутся в той же фазе, что и код, не потом.

- [x] **0. Каркас** — Cargo.toml, план, CI-скрипт `./check.sh` (fmt + clippy + test).
- [x] **1. Хранилище** — `Schema`, типизированные колонки (`I64/F64/Str/Bool/Vector`), `Table::insert/scan`.
      Тесты: round-trip, типы, границы.
- [x] **2. NEON-ядра** — `sum/min/max`, фильтр-маски, `dot`/`l2` для векторов, скалярный fallback.
      Тесты: совпадение NEON и скаляра на рандомных данных в пределах единиц ULP
      (побитово они и не обязаны совпадать — сложение `f32` не ассоциативно).
- [x] **3. SQL** — подмножество через `sqlparser`: SELECT, WHERE, GROUP BY, ORDER BY, LIMIT,
      агрегаты (count/sum/avg/min/max/uniq). Векторизованный исполнитель, rayon для скана.
      Тесты: 20+ запросов с эталонными ответами.
- [x] **4. Персистентность** — снапшот колонок на диск + WAL для дельты. Восстановление при старте.
      Тесты: kill-9 симуляция, WAL replay, битый WAL не убивает старт.
- [x] **5. Векторы** — `VECTOR(dim)` тип, KNN через `ORDER BY vec <-> $q LIMIT k`, cosine/L2/dot.
      Тесты: recall против брутфорса, размерности, нормализация.
- [x] **6. HTTP REST** — axum: `POST /query`, `POST /insert`, `GET /health`, `GET /schema`.
      Тесты: интеграционные через `tower::ServiceExt`.
- [x] **7. gRPC** — tonic, тот же сервис. Тесты: in-process клиент-сервер.
- [x] **8. CLI** — `veldbctl`, rustyline: автокомплит по ключевым словам SQL + именам таблиц/колонок
      (тянутся с сервера), история, многострочный ввод.
- [x] **9. Репликация** — async primary→replica отгрузка WAL по TCP, replica read-only,
      LSN-квитирование, догон с середины. Тесты: два инстанса в одном процессе, сходимость.
- [x] **10. ClickBench** — загрузчик `hits.tsv`, 43 запроса, раннер с медианой из 3 прогонов,
      отчёт в Markdown. Итерации тюнинга по профилю.
- [~] **11. Raspberry Pi** — `--max-memory` вместо OOM-killer, systemd-юнит, скрипт
      кросс-сборки, документация. **Не закрыто:** сборка под `aarch64-unknown-linux-gnu`
      в этом окружении не выполнялась (нет кросс-компилятора C для `psm`), на живом
      устройстве не проверялась. См. `docs/raspberry-pi.md`.

## Итог

Все фазы, кроме проверки на живом Raspberry Pi, закрыты. 95 тестов, `clippy -D warnings`
чист, ClickBench проходит 42 запроса из 43. Найденные по ходу и починенные баги:

- подстановка агрегатов и ключей группировки затирала друг друга в общем индексном
  пространстве промежуточного кадра (`GROUP BY` по не-первой колонке возвращал ключ
  вместо агрегата) — заменено на подстановку за один проход;
- `LIKE` с шаблоном, привязанным с обеих сторон одним куском (`'abc'`), совпадал с любой
  строкой, начинающейся на этот кусок;
- скалярная функция с литералом в аргументе паниковала на пустой выборке: длину брали
  как максимум по аргументам, а её задают только неконстантные (нашёл ClickBench Q40).

## Не делаем (пока)

- Транзакции/MVCC — снапшот-изоляция на чтение есть за счёт Arc-свопа колонок, полноценные
  транзакции добавим, если появится запись из нескольких клиентов в одну строку.
- UPDATE/DELETE точечные — колоночный append-only + tombstone-битмап, когда понадобится.
- Распределённый шардинг — сначала одна нода должна быть быстрой.
