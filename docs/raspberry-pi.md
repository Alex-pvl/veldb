# veldb на Raspberry Pi

## Что проверено, а что нет

Проверено: весь код собран и прогнан на **aarch64 (Apple M-серия, macOS)** — это та же
архитектура и те же NEON-интринсики, что на Pi 4/5 с 64-битной ОС.

**Не проверено:** сборка под `aarch64-unknown-linux-gnu` в этом окружении не выполнялась —
на машине нет кросс-компилятора C, а он нужен для `psm` (защита SQL-парсера от переполнения
стека). Три рабочих пути описаны в шапке `scripts/build-pi.sh`; самый надёжный — собрать
прямо на Pi. Пока эта сборка не прогнана на живом устройстве, считайте поддержку Pi
заявленной, а не подтверждённой.

## Требования

- Raspberry Pi 4 или 5, **64-битная** ОС. Проверьте:

  ```bash
  uname -m     # должно быть aarch64, а не armv7l
  ```

  На 32-битной ОС сборки не будет: код опирается на 64-битные указатели и NEON из aarch64.
  Kali, Raspberry Pi OS и Ubuntu for Pi выпускаются в обоих вариантах, и 32-битный
  ставится по недосмотру чаще, чем хотелось бы.

- Rust 1.85+ и зависимости сборки:

  ```bash
  sudo apt update
  sudo apt install -y protobuf-compiler build-essential pkg-config
  curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
  ```

  | Пакет | Зачем |
  |---|---|
  | `protobuf-compiler` | `build.rs` генерирует gRPC-код из `proto/veldb.proto` |
  | `build-essential` | компилятор C для `psm` (защита SQL-парсера от переполнения стека на вложенных скобках) |

## Сборка прямо на Pi

```bash
git clone https://github.com/alex-pvl/veldb.git && cd veldb
cargo build --release
```

10-20 минут на Pi 4. **На Pi с 4 ГБ сборка может упасть по памяти**: релизный профиль
собран с `lto = "fat"` и `codegen-units = 1`, и линковка съедает несколько гигабайт.

Если увидели `signal: 9, SIGKILL` или `collect2: fatal error: ld terminated` — это оно.
Два способа:

```bash
# 1. ослабить LTO только для этой сборки (бинарник процентов на 5-10 медленнее)
CARGO_PROFILE_RELEASE_LTO=thin \
CARGO_PROFILE_RELEASE_CODEGEN_UNITS=16 \
cargo build --release -j2

# 2. или дать swap и собрать полноценно
sudo dphys-swapfile swapoff
sudo sed -i 's/^CONF_SWAPSIZE=.*/CONF_SWAPSIZE=4096/' /etc/dphys-swapfile
sudo dphys-swapfile setup && sudo dphys-swapfile swapon
cargo build --release
```

Swap на SD-карте медленный и изнашивает её, поэтому второй способ — для разового
случая. Регулярно пересобирать лучше с `thin`, а ещё лучше — брать готовый бинарник
из релиза (`aarch64-unknown-linux-gnu`) и не собирать на Pi вовсе.

## Сколько данных влезет

veldb держит данные в памяти целиком. Ориентир по замеру на схеме ClickBench
(105 колонок, все целые как `i64`): **~850 байт на строку**.

| Модель | ОЗУ | Разумный `--max-memory` | Строк схемы hits |
|---|---|---|---|
| Pi 4 | 4 ГБ | 2 GiB | ~2.5 млн |
| Pi 5 | 8 ГБ | 5 GiB | ~6 млн |

На узких таблицах цифра совсем другая: строка из пяти `INT` — это 40 байт, то есть
десятки миллионов строк на тех же 2 ГиБ. 850 байт — это про ClickBench, а не про veldb.

`--max-memory` не опция для галочки: без него переполнение заканчивается OOM-killer'ом,
который убивает процесс вместе с ещё не сброшенными на диск данными. С ним вставка
получает внятную ошибку, а всё уже записанное остаётся читаемым.

## Долговечность на SD-карте

`--durability fsync` (по умолчанию) делает `fsync` на каждый запрос с записью. На SD-карте
это единицы миллисекунд — заметно, но переживает выключение питания, что для Pi
как раз актуально.

`--durability buffered` убирает `fsync`: переживает падение процесса, но не потерю питания.
Разумный выбор, если Pi под UPS или если данные восстановимы из другого источника.
В `deploy/veldb.service` стоит `buffered` плюс автоснапшот раз в 5 минут — компромисс
в пользу ресурса SD-карты; поменяйте на `fsync`, если данные незаменимы.

## Реплика на Pi

Типовая схема: первичный узел на большой машине, Pi — читающая реплика.

```
veldb --data /var/lib/veldb --replicate-from 192.168.1.10:8080 --max-memory 2GiB
```

Реплика сама запрещает себе запись, поэтому случайно разъехаться с первичным узлом
она не может. При старте она забирает полный снапшот, дальше догоняет по WAL.

## Питание и охлаждение

Долгие сканы забивают все ядра (rayon), и Pi 4 без радиатора уходит в троттлинг за
пару минут. Если бенчмарк «плавает» от прогона к прогону — сначала посмотрите
`vcgencmd measure_temp`, а потом уже на профилировщик.
