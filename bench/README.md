# ClickBench на veldb

## Быстрая проверка без датасета

```
cargo build --release
./target/release/veldb-bench --gen 3000000 --runs 3 --out bench/report-gen-3m.md
```

`--gen` наполняет таблицу синтетическими данными с правдоподобными кардинальностями.
Это не замена настоящему ClickBench — распределения другие, — но харнесс так можно
проверить, не выкачивая 15 ГБ, и на нём же ловятся регрессии.

## На настоящих данных

```
wget https://datasets.clickhouse.com/hits_compatible/hits.tsv.gz
gzip -d hits.tsv.gz                                   # ~74 ГБ

./target/release/veldb-bench --tsv hits.tsv --rows 10000000 --runs 3 \
    --out bench/report-hits-10m.md
```

`--rows` обязателен на машине с обычным объёмом ОЗУ: см. ниже.

## Честно про размер датасета

Полный ClickBench — 100 млн строк. veldb держит данные в памяти целиком, и по замеру
на этой схеме выходит **~850 байт на строку**, то есть полные 100 млн потребовали бы
около **80 ГиБ ОЗУ**. Ни на 16-гигабайтном ноутбуке, ни тем более на Raspberry Pi
этого нет.

Поэтому в отчёте **всегда указывается число строк**, и сравнивать его надо с прогоном
ClickHouse на том же числе строк и той же машине. «10 млн у нас против 100 млн у них» —
это не бенчмарк.

Откуда берутся 850 байт: у veldb одна целочисленная ширина (`i64`), а в схеме hits
92 числовые колонки, которые ClickHouse хранит как `UInt8`/`UInt16`/`UInt32`. Это и есть
главный пункт для оптимизации, см. ниже.

## Результат последнего прогона

`bench/report-gen-3m.md` — 3 млн синтетических строк, MacBook на M-серии, 12 ядер:

- выполнено **42 из 43** запросов, суммарно **~5,1 с**;
- Q29 не выполняется: он использует `REGEXP_REPLACE`, а регулярок в veldb нет.
  Крейт `regex` добавим, когда они понадобятся не только бенчмарку — ради одного
  запроса из 43 тащить движок регулярок не стоит.

## Что оптимизировать дальше (по убыванию отдачи)

1. **Узкие целочисленные типы** (`INT8`/`INT16`/`INT32`). Сократит память на схеме hits
   примерно втрое, а вместе с ней — время всех сканов: они упираются в полосу памяти.
   Самый крупный пункт и по выигрышу, и по объёму работы.
2. **Поколоночное исполнение чанками по 64K строк.** Сейчас промежуточный массив
   материализуется на всю выборку: на 3 млн строк это 24 МБ на узел выражения, мимо всех
   кешей. Чанки удержат промежуточные данные в L2.
3. **Группировка по одной целочисленной колонке без склейки байтового ключа.**
   Q32/Q33 (группировка по почти уникальному `WatchID`) в этот ключ и упираются.
4. **Словарное кодирование строк низкой кардинальности.** Поможет `GROUP BY URL`
   и по памяти, и по скорости хеширования.

Каждый пункт — из профиля, а не из общих соображений. Порядок менять только по новым замерам.
